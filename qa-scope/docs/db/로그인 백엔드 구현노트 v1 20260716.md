### 2.1 SSR 쿠키 전달 (인증 도입이 드러낸 필수 후속)

페이지 SSR은 `lib/api/client.ts`의 `fetchApi()`로 **자기 자신의 /api 라우트를 HTTP fetch**하는
구조다(팀 원칙: 엔진과 화면은 JSON API로만 대화). 이 내부 fetch에는 브라우저 세션 쿠키가
자동으로 실리지 않아, proxy가 /api/*를 잠근 순간 **로그인한 사용자의 페이지 렌더조차 내부
401로 실패**한다. → `fetchApi`가 인입 요청의 쿠키(`next/headers`의 `cookies()`)를 그대로
전달하도록 수정했다. `next/headers`는 서버 전용이라 **동적 import** 사용 —
`ReviewPanel`(클라이언트 컴포넌트)이 `lib/api/evaluations.ts`를 import해 이 모듈이
클라이언트 번들에도 들어가기 때문(정적 import 시 클라이언트 빌드가 깨짐).

⚠ 같은 구조 때문에 `getBaseUrl()`의 `APP_PORT`가 **실제 서비스 포트와 일치**해야 한다.
다른 포트로 띄우면 SSR fetch가 엉뚱한 프로세스(예: 3000을 점유한 Docker Desktop)에 붙어
알 수 없는 오류(self-signed certificate 등)가 난다 — 로컬 검증 시 실제로 겪은 함정.

### ⚠ middleware.ts → proxy.ts (Next.js 16 규약)

설계문서는 `middleware.ts`로 적혀 있으나, **설치본이 Next.js 16.2.10**이고 16부터
`middleware.ts`가 **`proxy.ts`로 이름 변경**(기본 Node 런타임)되었다. 둘 다 있으면 빌드 에러,
`middleware.ts`는 deprecated 경고. 그래서 **개념은 동일(세션 가드 레이어)하되 파일명만 `proxy.ts`**로 구현했다.
부수 효과: proxy가 Node 런타임이라 edge 제약(bcrypt·mysql2 불가)이 사라졌지만, 관심사 분리를 위해
DB/bcrypt는 `auth.ts`(authorize)에만 두고 `proxy.ts`는 `auth.config.ts`(edge-safe)로 JWT 검증만 한다.
