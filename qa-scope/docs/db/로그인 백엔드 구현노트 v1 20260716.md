### 2.1 SSR 쿠키 전달 (인증 도입이 드러낸 필수 후속)

페이지 SSR은 `lib/api/client.ts`의 `fetchApi()`로 **자기 자신의 /api 라우트를 HTTP fetch**하는
구조다(팀 원칙: 엔진과 화면은 JSON API로만 대화). 이 내부 fetch에는 브라우저 세션 쿠키가
자동으로 실리지 않아, proxy가 /api/*를 잠근 순간 **로그인한 사용자의 페이지 렌더조차 내부
401로 실패**한다. → `fetchApi`가 인입 요청의 쿠키(`next/headers`의 `cookies()`)를 그대로
전달하도록 수정했다. `next/headers`는 서버 전용이라 **동적 import** 사용 —
`ReviewPanel`(클라이언트 컴포넌트)이 `lib/api/evaluations.ts`를 import해 이 모듈이
클라이언트 번들에도 들어가기 때문(정적 import 시 클라이언트 빌드가 깨짐).

⚠ 같은 구조 때문에 `getBaseUrl()`의 `APP_PORT`가 **실제 서비스 포트와 일치**해야 한다.
다른 포트로 띄우면 SSR fetch가 엉뚱한 프로세스(예: 3000을 점유한 Docker Desktop)에 붙어
알 수 없는 오류(self-signed certificate 등)가 난다 — 로컬 검증 시 실제로 겪은 함정.

### ⚠ middleware.ts → proxy.ts (Next.js 16 규약)

설계문서는 `middleware.ts`로 적혀 있으나, **설치본이 Next.js 16.2.10**이고 16부터
`middleware.ts`가 **`proxy.ts`로 이름 변경**(기본 Node 런타임)되었다. 둘 다 있으면 빌드 에러,
`middleware.ts`는 deprecated 경고. 그래서 **개념은 동일(세션 가드 레이어)하되 파일명만 `proxy.ts`**로 구현했다.
부수 효과: proxy가 Node 런타임이라 edge 제약(bcrypt·mysql2 불가)이 사라졌지만, 관심사 분리를 위해
DB/bcrypt는 `auth.ts`(authorize)에만 두고 `proxy.ts`는 `auth.config.ts`(edge-safe)로 JWT 검증만 한다.

## 9. `/login`·로그아웃 임시 구현 + UI 담당 인수인계

검증용 최소 구현(디자인 무관, 토큰만 사용). **UI 담당은 아래를 지키면 자유롭게 교체 가능.**

**추가/수정 파일**
- `app/login/page.tsx` — 서버 컴포넌트. `?callbackUrl` 수신, 이미 로그인 시 목적지로 redirect, 오픈 리다이렉트 방지(상대경로만).
- `app/login/actions.ts` — `'use server'` `loginAction`. `signIn('credentials', …)` 호출, 실패 코드 분기.
- `components/login/LoginForm.tsx` — `'use client'`. `useActionState`로 에러 문구 인라인 표시.
- `components/auth/UserMenu.tsx` — 서버 컴포넌트. `display_name` + 로그아웃(인라인 서버 액션 `signOut`).
- `app/layout.tsx` — 헤더 우측에 `<UserMenu />` 추가.

**UI 담당이 반드시 지킬 것(계약)**
1. 폼 필드 `name`은 **`username`·`password`**, 히든 **`callbackUrl`** 유지(서버 액션이 이 이름으로 읽음).
2. 실패 문구 2종만: 일반=`아이디 또는 비밀번호가 올바르지 않습니다` / `code==='RateLimited'`=`잠시 후 다시 시도해 주세요`. **어느 쪽이 틀렸는지 구분 노출 금지**(§5).
3. **회원가입·비밀번호 찾기 링크 추가 금지**(관리자 발급 구조 — 존재 자체가 모순, §5).
4. 색은 **globals.css 토큰만**(하드코딩 금지). 현재 폼도 토큰만 사용.
5. 로그인 방식은 서버 액션(`loginAction`) 유지 권장. 클라이언트 `signIn`으로 바꾸려면
   `redirect:false` 반환값에서 `code`가 안 실려 RateLimited 구분이 어려움 — 서버 액션이 이 점에서 유리.

**주의(함정)**
- 헤더(`UserMenu`)가 매 페이지에서 `auth()`를 부른다 → layout이 동적. 정상(앱이 이미 DB로 동적).
- `/login`은 proxy matcher 예외라 열려 있음. 새 공개 페이지(예: 안내 페이지)를 열려면 matcher도 함께 손봐야 함.
- 로그아웃은 `signOut({ redirectTo: '/login' })`. 위치/문구만 바꾸고 이 호출은 유지.
