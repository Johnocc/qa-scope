# 화면② 채점 상세 — API 응답 계약 v1.2

> **목적:** 프론트엔드(화면② 목업 → Next.js 이식)와 백엔드가 병렬로 작업하기 위한
> **데이터 약속 문서**다. 화면④ 계약과 같은 원칙을 따르되,
> 이 화면의 API는 **이미 구현되어 있다** (`app/api/evaluations/[id]/route.ts` +
> `lib/db/evaluationRepo.ts → getFullEvaluation()`).
> 따라서 이 문서는 "새 설계"가 아니라 **현재 구현을 정본화**하고,
> 목업 헤더에 필요한 최소 보강(`header` 블록)을 추가로 확정한 것이다.
>
> **v1.1 (2026-07-11):** 검수(리뷰) 쓰기 계약 확정(`검수_쓰기_API계약_v1.md`,
> 2026-07-10)에 따라 응답에 **`review` 블록**(§3.4)을 추가했다. 검수가 없으면
> `null` — 기존 3블록만 쓰는 프론트 코드는 무수정으로 동작한다.

---

## 0. 쉬운 설명 (개발 배경을 모르는 팀원용)

- 화면②는 "상담 1건의 성적표 + 원문"이다. 좌측에 상담 원문(발화 목록),
  우측에 18항목 점수를 놓고, **항목을 클릭하면 근거 발화로 점프**한다.
- 점프가 되는 이유: 채점 때 AI가 인용한 근거마다 그 인용이 실제로 있었던
  발화의 `dialogue_id`를 파이프라인(인용 대조 — 안전망②)이 확정해서 저장해
  두었기 때문이다. 프론트는 이 ID로 좌우를 연결만 하면 된다.
- 우측 평가 데이터는 **출력스키마 ver2(한글 키) 그대로**다. 새 스키마를
  또 만들지 않는다 — 이유는 §1 결정 1.

## 1. 확정 결정 사항

| # | 결정 | 내용 · 이유 |
|---|---|---|
| 1 | **`evaluation` 블록 = 출력스키마 ver2 한글 키 (예외 허용)** | 앱 API는 원칙적으로 snake_case지만(화면④ 계약 결정 1), 이 화면은 "평가 1건 원본"을 보여주는 화면이고 ver2가 이미 팀의 단일 계약(CLAUDE.md §7.2)이다. 영문으로 한 번 더 변환하면 스키마 2벌 유지 비용 + 변환 버그 위험만 생김. 일관성만 따지자면 블록 이름을 영문으로 바꾸어야 하겠지만, 한글 이름이 LLM 계약 원본인데다가 번역 레이어가 감사 추적성을 깨고 유지비만 늘리기 때문이다. 만약 영문으로 통일해야만 하는 상황이 생기면 그때 영문 뷰를 따로 붙이도록 한다. **한글 키 = LLM 계약 영역**이라는 역할 분리에 부합 |
| 2 | **조회 키 = `evaluation_id` (내부 PK)** | 화면① `items[].evaluation_id`에서 링크로 진입. **⚠ 재채점 시 새로 발급됨** — URL 북마크·외부 시스템 참조 키로 쓰지 말 것 (재채점=덮어쓰기, 팀 결정 2026-07-06) |
| 3 | **점프 연결 키 = `근거[].dialogue_id` ↔ `dialogues[].dialogue_id`** | 숫자 내부 키로 매칭 (목업의 "대화ID 뒤 3자리" 방식 대체). `대화ID`(=`dialogue_code`, 예: `C-2026-018442-002`)는 표시·대조용으로 병행 제공 |
| 4 | **근거는 배열** | 항목 1개에 근거 여러 개 가능 (DB 3-D 구조). 목업은 단일 `근거대화ID`였음 → 프론트는 배열 기준으로 구현 (첫 근거로 점프, 나머지는 목록 표시 등) |
| 5 | **헤더 정보는 `header` 블록(snake_case)으로 분리** | 목업 헤더(상담사명·유형·위험 태그·상태 배지)에 필요한 값을 서버가 계산해 별도 블록으로 제공. `status_labels` 병기 규칙은 **화면① 계약 §3.3과 동일** (화면①↔② 배지 불일치 방지) |
| 6 | **N/A 항목도 18개 안에 포함** | `충족수준: "해당없음"`, `근거: []`, `획득점수: 0`. 프론트는 N/A 칩 표시 + "근거 발화 없음" 안내 (화면④ 계약 결정 2와 같은 원칙) |

## 2. 엔드포인트

```
GET /api/evaluations/{evaluation_id}
```

| 파라미터 | 위치 | 값 | 설명 |
|---|---|---|---|
| `evaluation_id` | path | 양의 정수 | 평가 PK (화면① 목록에서 전달받음) |

- 성공: `200` + 아래 §3 형태의 JSON
- 잘못된 ID(숫자 아님·0 이하): `400` + `{ "error": "잘못된 평가 ID" }`
- 존재하지 않는 평가: `404` + `{ "error": "평가를 찾을 수 없음" }`
- 서버 오류: `500` + `{ "error": "<메시지>" }`

## 3. 응답 구조 (블록 4개 — ★v1.1에서 `review` 추가)

화면 요소와의 대응:

| 응답 블록 | 화면② 요소 | 키 표기 |
|---|---|---|
| `header` | 상단 헤더 (상담번호·상담사·유형·위험 태그·상태 배지) | snake_case |
| `evaluation` | 우측 패널 (18항목·총점·플래그·요약) | **ver2 한글 키** (결정 1) |
| `dialogues` | 좌측 상담 원문 (turn_order 순) | snake_case |
| `review` ★v1.1 | 하단 검수 영역 (검수 상태·검수자·코멘트·수정 내역·유효 점수). 검수 없으면 `null` | snake_case |

**★v1.2 — SummaryPanel 신설 (우측 패널 최상단):**

| 응답 데이터 | 기존 표시 위치 | 변경 후 |
|---|---|---|
| 표시 점수 (검수 유효값 우선 COALESCE — 검수 쓰기 계약 §4) | 상단 헤더 | **SummaryPanel 좌측 큰 점수** |
| `status_labels` 상태 배지 (검수 유효값 우선) | 상단 헤더 | **SummaryPanel** (점수 옆) |
| `evaluation.항목평가` 18항목 | 우측 항목 카드만 | 항목 카드 + **SummaryPanel 가로 막대 리스트** (신규 뷰) |
| 위험 점(RiskDot) | 상단 헤더 | 상단 헤더 **유지** (변경 없음) |

**SummaryPanel 막대 렌더 규칙 (코드 정본):**
- 막대 폭 = `획득점수 ÷ 배점` 비율
- `충족수준 = '미충족'` → 연빨강 풀바 (미충족 강조)
- `충족수준 = '해당없음'` → 막대 없음, `—` 톤다운
- 점수·배지의 데이터 소스와 COALESCE 규칙은 v1.1 §3.4 + 검수 쓰기 계약 §4 그대로 — 본 개정에서 변경하지 않음

**헤더 정리:** 점수·상태 배지는 헤더에서 제거 (SummaryPanel로 일원화 — 같은 값 두 곳 표시 방지). 헤더 잔류 요소: 상담번호 타이틀, 상담사명 + [리포트 보기] 버튼(화면③과 표기 통일), 유형, RiskDot, [← 목록] 버튼.
→ `header` 블록 필드는 전부 유지 (RiskDot·타이틀·상담사명이 계속 사용).

### 3.1 `header` — 상단 헤더 (★신규 보강 — §6 남은 일)

| 필드 | 타입 | 설명 |
|---|---|---|
| `consultation_code` | string | 상담번호 (예: `dummy_01`) — 헤더 타이틀 |
| `agent_id` | string | 상담사 ID. 미배정은 `"unknown"` |
| `agent_name` | string | 상담사 이름 (명부 `agents`). `unknown`은 `"미배정"` |
| `consulted_at` | string(date-time) | 상담 시작 일시 |
| `consult_type` | string\|null | AI 판정 상담유형 (`evaluation.분류.상담유형`과 동일 값) |
| `risk_flagged` | boolean | `true`면 "● 위험" 태그 (라벨과 별개 레이어 — §8.4) |
| `status_labels` | string[] | 병기 배열 — 판정 규칙·순서는 **화면① 계약 §3.3 정본**을 따름 |

### 3.2 `evaluation` — 평가 1건 (출력스키마 ver2 재조립본)

`getFullEvaluation()`이 반환하는 현재 형태 그대로. 최상위 필드:

| 필드 | 타입 | 설명 |
|---|---|---|
| `상담ID` | string | = `header.consultation_code` |
| `evaluation_id` | number | 평가 PK 에코 |
| `평가메타` | object | `평가주체`·`AI모델`·`루브릭버전`·`평가일시`·`검증통과회차` |
| `분류` | object | `상담유형`·`유형근거`·`권유유형`·`권유근거` |
| `판매정보` | object\|null | 신규판매 상담만 객체, 그 외 `null` (ver2 규약). `권유상품코드`·`권유상품명`·`니즈시나리오코드`·`매칭판정`·`확인절차{가입목적·재정상황·기존계약}`·`판정근거` |
| `항목평가` | array(18) | 아래 상세. **항상 18개, A1→E2 루브릭 순** |
| `위험플래그` | array | `{규칙번호, 관련항목코드, 근거}` — 감지된 것만, 없으면 `[]` |
| `집계` | object | `원점수합`·`적용배점합`·`환산총점`·`위험표시여부`·`상태라벨` — **전부 코드 재계산 저장값** (LLM 산출 미신뢰 원칙) |
| `고객만족` | object | `등급`·`점수`·`근거` |
| `요약` / `종합피드백` | string | 텍스트 블록 |

`항목평가[]` 원소:

| 필드 | 타입 | 설명 |
|---|---|---|
| `항목코드` | string | `"A1"`~`"E2"` |
| `충족수준` | string | `충족` / `부분충족` / `미충족` / `해당없음` |
| `배점` | number | 루브릭 v1.5 고정값 (`lib/scoring/constants.ts` 정본) |
| `획득점수` | number | 규칙값 (충족=배점 / 부분충족=배점÷2 / 미충족·해당없음=0) |
| `근거` | array | 아래 상세 (결정 4 — 배열) |
| `코멘트` | string\|null | 판정 코멘트. N/A는 사유가 여기 들어옴 |

`근거[]` 원소:

| 필드 | 타입 | 설명 |
|---|---|---|
| `대화ID` | string\|null | `dialogue_code` (예: `dummy_01-002`) — 표시용 |
| `dialogue_id` | number\|null | **점프용 내부 키** (결정 3). 인용 대조 실패(환각 의심) 건은 `null` |
| `인용문` | string | 원문 그대로 인용 (안전망②에서 대조된 문자열) |

> 항목명(`A1: 맞이인사…`)·영역명은 응답에 없다 — 루브릭 v1.5 고정값이므로
> 프론트 상수로 유지 (목업의 `ITEM_NAMES`/`DOMAIN_NAMES` 방식 그대로.
> 단 영역 표시명은 화면③·④와 통일: C=`태도·공감` — 화면④ 계약 §3.2 매핑 참조.
> C 영역에 '경청' 키워드 사용 금지: A영역(A3 경청 및 용건·니즈 파악)과 겹침 — 팀 결정 2026-07-09).

### 3.3 `dialogues` — 좌측 상담 원문 (turn_order 오름차순)

| 필드 | 타입 | 설명 |
|---|---|---|
| `dialogue_id` | number | 발화 PK — 점프 타깃 (`근거[].dialogue_id`와 매칭) |
| `dialogue_code` | string\|null | 대외 발화 코드 |
| `turn_order` | number | 상담 내 순서 (1부터) |
| `speaker` | string | `"상담사"` / `"고객"` — 말풍선 좌우 구분 |
| `spoken_at` | string(date-time) | 발화 시각 |
| `offset_sec` | number\|null | 상담 시작 기준 상대 초 → 목업의 `[00:05]` 타임스탬프 표기는 이 값으로 렌더 (`null`이면 `spoken_at` 차이로 대체 가능) |
| `content` | string | 발화 원문 |

### 3.4 `review` — 검수 블록 (★v1.1 신설 — 검수 없으면 `null`)

형태는 **검수 쓰기 계약 §3.1 응답의 `review`와 동일** (단일 정의 — 정본은
`검수_쓰기_API계약_v1.md`). 스텁: `schemas/review.v1.example.json`.

| 필드 | 타입 | 설명 |
|---|---|---|
| `review_id` | number | 검수 PK |
| `evaluation_id` | number | 대상 평가 에코 |
| `review_status` | string | `"검수중"` / `"확정"` — 확정 건은 재채점 기본 스킵 보호 |
| `reviewer` | string | 검수자 (MVP: 자유 문자열) |
| `review_comment` | string\|null | 검수 코멘트 |
| `overrides` | array | 항목별 수정 내역 `{item_code, level_original, level_override, override_reason}` — 수정한 항목만. 쓰기 v0 단계에서는 항상 `[]` |
| `effective` | object | 검수 반영 유효 집계 `{final_score, status_label, risk_flagged, status_labels[]}` — override 없으면 AI 값과 동일 |
| `reviewed_at` | string(date-time) | 마지막 검수 수정 시각 |

**프론트 표시 규칙 (검수 쓰기 계약 §4 — 이원화):**
- 총점·상태 배지는 `review.effective` 우선, `review === null`이면 AI 원본
  (`집계`·`header.status_labels`) — `COALESCE(유효값, AI 원본)`.
- `overrides[]`는 AI 판정(`level_original`) vs 검수자 판정(`level_override`)
  diff로 병기 표시.
- 검수 저장·철회는 별도 쓰기 API — `PUT`/`DELETE /api/evaluations/{id}/review`
  (요청·응답·에러는 검수 쓰기 계약 §3.1·§3.2 정본).

## 4. 점프 동작 규약 (프론트 구현 기준)

1. 항목 클릭 → `근거[0].dialogue_id`로 좌측 `dialogues` 중 해당 발화 하이라이트 + 스크롤.
2. `근거`가 2개 이상이면 첫 근거로 점프, 나머지는 항목 상세에서 선택 가능하게.
3. `충족수준 === "해당없음"` → 점프 없음, "해당없음(N/A)이라 근거 발화가 없습니다" 안내.
4. `dialogue_id === null` (인용 대조 실패 건) → 점프 없음, `인용문` 텍스트만 표시.
   0건이어야 정상이지만 방어적으로 처리 (안전망② 통과본만 저장되는 게 원칙).
5. ★v1.2 — SummaryPanel 각 행 클릭 → `#item-{항목코드}` 앵커 이동 (`ItemScorePanel` 각 항목 카드에
   `id="item-{코드}"` 신설). 기존 항목→발화 점프 규약(1~4)은 변경 없음.

| 재채점 후 조회 ★v1.1 | 새 평가의 `review`는 `null` (검수는 자동 승계되지 않음 — 쓰기 계약 §5. 이전 검수는 3-E '검수폐기' 로그에 보존) |
